# docs/history/ —— 记录与证据

> 这个目录**只追加、不回改**。每一条记录的日期与结论就是证据，事后调整会毁掉"可复现"这个唯一价值。
> 现状看 [../STATUS.md](../STATUS.md)；怎么办事看 [../HANDOFF.md](../HANDOFF.md) 与 [../ops/](../ops/)。

## 1. 两篇文档的分工

| 文档 | 记什么 | 不记什么 |
| --- | --- | --- |
| [TESTLOG.md](TESTLOG.md) | **跑过什么、输出什么、结论是什么**（命令 + ≤5 行摘要 + 结论） | 不贴长日志全文；不讲原理 |
| [BUG_CASES.md](BUG_CASES.md) | **这个 bug 为什么会发生、怎么一眼看出来、下次怎么办**（原理 + 代码位置 + 定位手法 + 面试说法） | 不重复测试结论（引用 TESTLOG 的 § 号即可） |

一句话：**TESTLOG 是证据，BUG_CASES 是原理**。同一个修复在两处各写一半，不能互相替代。

## 2. TESTLOG 的三级粒度（写之前先选级）

| 级别 | 什么时候写 | 篇幅 | 估时 |
| --- | --- | --- | --- |
| **L1 冒烟** | 每次改完代码、跑了构建或一个二进制 | 表格 1 行 | 30 秒 |
| **L2 任务** | 完成一个任务（T1/T2/…）或修掉一个 P0/P1 | 5–15 行小节 | 2 分钟 |
| **L3 里程碑** | M1/M2 收尾、长时间压测 | 独立一节 | 10 分钟 |

**硬规定**：修复类改动（P0/P1）在**提交前**必须有一条 L2 —— 否则事后无法证明"修好了"（对应 HANDOFF §2 红线 6「没实际执行不许声称通过」）。

L1 一行的格式：

```text
| 2026-11-14 | 崩溃采集补齐 | `make` RC=0；`scripts/coredump/check_coredump_env.sh` → PASS=5 WARN=9 FAIL=0 | ✅ |
```

## 3. BUG_CASES 的收录标准（四条满足任意一条就要写）

1. **现象与根因不在同一层**（画面坏在采集侧 → 实际根因在编码侧偏移计算）；
2. **只在特定并发 / 时序 / 内存残留下复现**（跑几十帧才停摆）；
3. **涉及资源所有权、生命周期、跨组件共享状态**（谁负责 `release`、谁负责 `delete`）；
4. **曾被误判过方向**（查了半天发现不是那回事）。

纯笔误 / 拼写 / 一行空指针且无连带语义 → **只在 [../STATUS.md](../STATUS.md) 标注**，不进本文。

每个案例必须有这 6 段（缺一段就会被追问）：

```text
现象 → 精确位置（文件 + 函数）→ 根因原理 → 修复 → 为什么难发现 → 面试怎么讲
```

并更新 `BUG_CASES.md` **§1 索引表**（`# | 症状 | 根因 | 提交 | 详见`）。

## 4. 引用方式

- 从别的文档引用一条测试：`TESTLOG.md §5.20`（用 § 号，不要用行号 —— 行号每次追加都会漂移）。
- 从别的文档引用一个案例：`BUG_CASES.md §2.12（B12）`。
- 本目录内部引用另一篇：`[BUG_CASES.md](BUG_CASES.md)`（同目录，直接写文件名）。
