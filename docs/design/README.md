## 2. 设计文档的写作要求

一篇合格的设计文档必须同时给出这四样，缺一样就会在落地时被重新讨论一遍：

| 要素 | 要求 | 反例 |
| --- | --- | --- |
| **判据** | 用什么标准筛出「该上提 / 该拆分」的对象 | "感觉媒体服务应该独立" |
| **取舍** | 至少 2 个备选方案 + 为什么淘汰 | 只写了最终方案 |
| **形状** | 目录、文件名、类/接口签名（能直接照着写代码） | "加一个管理层" |
| **顺序** | 拆成可独立验收的步骤（T4/T5/…），每步有验收判据 | "一次性重构" |

`DESIGN_MULTI_PIPELINE.md` 是本文档目录的范例：§0 一页结论、§3 判据筛出 16 项、§6 方案 A/B/C/D 对比、§7 拆成 T10a/T10b 顺序落地。

## 3. 状态标记约定（写新设计时照抄）

文档开头必须有一行状态，取值只用这四个：

```text
> 状态：**规划（未落地）**         —— 只有想法与设计，代码没有对应实现
> 状态：**设计提案，尚未实现**     —— 同上的另一种写法，保持原文不改
> 状态：**已部分落地**            —— 指明哪几个任务号已实现、哪些没有
> 状态：**已落地（YYYY-MM-DD）**   —— 全部实现，链接到 TESTLOG 的验收记录
```

落地进度变化时**只改状态行与「落地程度」列**，正文的设计推理保留（它记录的是"当时为什么这么选"，不是"现在是什么样"）。

## 4. 与其他目录的关系

```text
design/（为什么这么设计）
   ↓ 落地成任务 T2/T3/T5/T6/T7/T10a…
src/（代码）+ config/（配置）+ scripts/tests/（验收脚本）
   ↓ 跑出结果
history/TESTLOG.md（证据）· history/BUG_CASES.md（踩到的坑）
   ↓ 现状收敛
../STATUS.md（完成度与剩余问题）· ../HANDOFF.md（红线与任务索引）
```
